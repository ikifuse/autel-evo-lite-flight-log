# 不変条件（システム前提と保護ルール）

本書は変更時に横断確認する保護条件の正本。一般的な開発慣行だけを理由に変更・撤廃しない。設計理由・採用根拠は参照先の設計章、形式・数値・操作手順は担当専門docsで管理する。

## 1. Spreadsheetの手動編集と人間優先の原則

保存完了後の目視確認・訂正・補記・空欄整理は正規運用である。意図した手修正を異常・改ざん扱いして自動復元・破棄しない。pending中の対象セルはbefore/intended以外なら競合停止する。業務帳票としての理由と補記の範囲は [設計第5章](../01_ドローン運航記録_設計書/05_記録・手動補記.md) に従う。

## 2. 固定保存計画（Fixed Commit Plan）とロールフォワード

- 書込先・値を固定してScript Propertiesへ永続化し、再試行は元のplan・planHashを使う。新コード・点検カタログ・現在の空き場所から再生成しない。
- 巻戻しではなくセルの再照合と未反映部分の前方復旧で完了する。進捗METAだけを根拠にreadbackを省かない。
- active reservationと固定totalTargetsを維持し、未解決の別draftがあれば新規計画を止める。Lock内の直前再診断・書込順を守る。
- Developer Metadataの存在・読書きを保存成功・復旧・ownershipの条件にしない。Lock短縮・flush/readback削減は別途実GAS検証を伴う変更として扱う。

固定する理由は [設計第4章](../01_ドローン運航記録_設計書/04_保存・復旧.md)、技術契約は [architecture第9節](architecture.md#9-固定保存計画の詳細契約) に置く。

## 3. UUID冪等性と再送安全性

1運航を `op_` + UUID v4で識別する。有効なcomplete証明と同一入力署名がある再送は業務セルへ書かず成功応答し、同UUIDの入力変更は拒否する。complete証明は無期限保持し、容量不足でも追い出さず新規保存を止める。30日は詳細縮小の時期であり削除期限ではない。消失済み旧証明は保証対象外とし、[移行条件](rebuild-guide.md#保存証明と旧pendingの移行条件)を確認する。

## 4. バッテリー履歴（BAT）の重複防止と再利用

BAT行はplan作成時に固定し、再試行で選び直さない。セルがintendedならskip、beforeなら書込み、第三値なら停止する。complete後に利用者が空欄化した行は新しいUUIDで再利用できる。固定枠と探索条件は [Spreadsheet仕様5](spreadsheet-spec.md#5-バッテリー個別シートbat_1--bat_7仕様)、履歴の役割は [設計第6章](../01_ドローン運航記録_設計書/06_機体・バッテリー・累計.md) に従う。

## 5. 機体公式累計の独立性と二重加算防止

飛行行の途中累計と原本の正式累計を区別し、通常運航の確定時に機体ごとに独立加算する。現在の原本値を読み、管理開始の00:00を毎回のリセットに使わない。不明な過去時間を推測・逆算しない。機体別の起算理由・確認範囲は [設計第7章](../01_ドローン運航記録_設計書/07_点検整備・管理開始.md#機体別の累計起算根拠)、セルの検出・計算は [Spreadsheet仕様6](spreadsheet-spec.md#6-機体原本と機体累計時間仕様) に置く。

## 6. アプリテスト（TEST運航）の完全分離

TEST日付帳票と通常帳票を分離し、TESTで機体原本の正式累計を更新しない。BAT履歴は実際に1飛行1行を記録するため、TESTを無書込み試験とは扱わない。判定は `isAppTestPurpose_` に集約し、気象付記を含む目的の条件は [Spreadsheet仕様4](spreadsheet-spec.md#4-test日付シート仕様)、疑似運航と実飛行の区別は [設計第6章](../01_ドローン運航記録_設計書/06_機体・バッテリー・累計.md#アプリテストと実飛行) に従う。

## 7. 帳票の物理構造（1ブロック最大7飛行・1飛行1行）

各飛行を合算・省略せず1行ずつ残し、最大7飛行の帳票枠を超えない。ブロックと連番への割当ては [Spreadsheet仕様3](spreadsheet-spec.md#3-日常点検シート仕様) に従う。0飛行の点検保存も正規仕様としてサーバーで拒絶せず、BAT行・正式累計を増やさない。画面上の異常中止と0飛行保存の違いは [設計第3章](../01_ドローン運航記録_設計書/03_画面・運航フロー.md#飛行前点検) を参照する。

## 8. 数式インジェクション（Formula Injection）対策

自由入力の危険な先頭文字（制御文字・空白を含む）を数式として実行させずRichTextで保存する。固定計画作成時に一度だけ安全化し、再試行で二重変換しない。出力後のgetFormula空文字を試験することと、現行readbackが値・書式だけを比較することを区別する。[設計第8章](../01_ドローン運航記録_設計書/08_セキュリティ・品質.md#入力と表示の安全性)、[安全境界](architecture.md#6-セキュリティ境界と制約)、[試験](test-spec.md#61-数式インジェクションformula-injection対策の検証)に従う。

## 9. ワンオペ現場操作の最小化

確認可能な必要最小限の入力に絞る。同一機体での連続飛行・BAT交換で前点検11項目を繰り返さず、補助者や点検の合格を初期値で自動選択しない。操作負担と虚偽記録を避ける判断基準は [設計第1章](../01_ドローン運航記録_設計書/01_設計思想・基本方針.md#目的と判断基準)、引用・点検・BAT確認の動作は [第3章](../01_ドローン運航記録_設計書/03_画面・運航フロー.md) に従う。

## 10. ソースの正本とビルドの一貫性

srcを正本としdistを直接編集しない。コード構造整理でPropertiesキー、plan version、canonical JSON、operation順、公開GAS入口6関数と内部名を維持する。ロジック変更の回帰・ビルド整合性、コード構造整理のサーバー/Web互換・境界を [試験選択](test-spec.md#8-テスト実行コマンドと合否判定) に従って確認する。

## 11. 新規planの必須帳票欄（RC追加）

必須欄を黙って省略してcompleteしない。条件付きの必須欄・検出限界・停止前に原本コピー等が残る場合は [Spreadsheet仕様9](spreadsheet-spec.md#9-新規保存時の必須帳票検査) に従う。既存pendingをこの検査のために再生成せず、complete後の帳票訂正も検査・復元の対象にしない。

## 12. 正式記録全体による法令評価と決定済み運用

Webアプリ、帳票、原本複製による整備実施記録、必要時の補記を合わせて評価する。欄の不在や自動化の有無だけで不適合・未実装とせず、予定を実績にしない。原則・例外・柔軟規定・実運用・確認範囲を合わせた評価と、新事実がない限り採用済み事項を再問題化しない条件は [設計第2章](../01_ドローン運航記録_設計書/02_法令・運用.md#今後の法令調査監査ルール) を正本とする。手動補記は [第5章](../01_ドローン運航記録_設計書/05_記録・手動補記.md)、機体別起算は [第7章](../01_ドローン運航記録_設計書/07_点検整備・管理開始.md) に従う。

## 13. 手修正後の計算継続

導入済み集計では利用者の修正値を新しい基準にし、以後の差分を反映する。過去記録の帳尻合わせをせず、独自数式を尊重し、TEST疑似履歴を以後のBAT実績集計に加えない。通常の機体正式累計との役割分担は [設計第6章](../01_ドローン運航記録_設計書/06_機体・バッテリー・累計.md#手修正を基準とした計算継続)、対象・式・限界は [Spreadsheet仕様8](spreadsheet-spec.md#8-手修正後の計算継続導入型) に従う。
