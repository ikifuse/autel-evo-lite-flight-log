## 1. 文書の位置づけ

本書は、Autel EVO Lite / Lite+ ドローン運航記録システムにおけるGoogleスプレッドシート（帳票および原本）の物理構造・セル配置・書式・記録ルールを定めた正式仕様書である。

- 関連正本仕様書: [01設計書の目次](../01_ドローン運航記録_設計書/00_目次.md)
- コード対応索引: [docs/code-map.md](code-map.md)

## 2. 必須シートと原本構成

本システムは、固定スプレッドシート内の以下のシート群を対象として動作する。

| シート名 | 役割 | 備考 |
|---|---|---|
| `日常点検` | 日付シート複製用原本テンプレート | No.1およびNo.2の2ブロックを持つ |
| `BAT_1` ～ `BAT_7` | バッテリー個別履歴シート（計7枚） | 13～212行がデータ履歴領域 |
| `点検整備記録_EVO Lite_原本` | EVO Lite専用の累計管理・原本 | 点検時の総飛行時間セルを保持 |
| `点検整備記録_EVO Lite+_原本` | EVO Lite+専用の累計管理・原本 | 点検時の総飛行時間セルを保持 |

## 3. 日常点検シート仕様

### 3.1 シート生成と命名規則

- 日付シートはテンプレート原本 `日常点検` を複製して作成する。
- 新規コピーのNo.1 / No.2飛行記録見出しを `総飛行時間（HH:MM）` に設定する。原本と既存日付シートは変更しない。旧見出し `総飛行時間` / `総飛行時間（累計時間）` も保存時に認識する。TEST・連番も同じ。
- 通常シート名: `YYYY.M.D`（例: `2026.9.7`）。
- 同一日の複数運航: 既に同日シートが存在しブロックに空きがない場合、または「本日別の新しい現場」として運航を開始した場合は、連番サフィックスを付与して新規作成する（例: `2026.9.7_2`, `2026.9.7_3`）。
- 「本日別の新しい現場」フラグが有効な場合、既存シートに空きブロックがあっても連番シートを新規作成してそこへ記録する。

### 3.2 ブロック構造

1枚の日常点検シートは、左右2つの記録ブロック（No.1 / No.2）で構成される。

| ブロック | 列範囲 | 最大飛行回数 | 備考 |
|---|---|---:|---|
| No.1 | C:O（3～15列） | 7飛行 | 1運航目の開始、または機体交代・8飛行目の受け皿 |
| No.2 | R:AD（18～30列） | 7飛行 | 同一日の2運航目、8飛行目以降、または交代機体 |

- 同一機体で8飛行目が発生した場合は、次の空きブロックへ記録を送る。
- 同一運航内で機体交代（EVO Lite ↔ EVO Lite+）を行った場合も、交代先機体は次の空きブロックを使用する。
- 1つのブロックに8行以上書き込むことは絶対にせず、両ブロックが使用済みの場合は次の連番日付シートを作成する。

### 3.3 ブロック内レイアウトと記録項目

各ブロックには以下の項目を配置・記録する。元の列幅、行高、セル結合、外観罫線はテンプレート原本の設定を維持し、変更しない。

1. **基本情報ヘッダー**: 機体名・登録記号、実施日、飛行目的、操縦者／補助者氏名、技能証明番号、飛行経路・場所、飛行カテゴリー、飛行方法。
2. **飛行前点検**: 11項目の点検結果（チェック欄に `☑` または `□` を記録）。
3. **飛行記録行（最大7行）**:
   - 飛行行の開始位置は固定行番号ではなく、見出しセル「使用バッテリー」を検索して動的に特定する。
4. **飛行後点検**: 4項目の点検結果（機体全般、プロペラ・フレーム、発熱、その他）、点検実施場所、異常の有無、不具合詳細、確認者。

### 3.4 飛行記録行の列構成

見出し「使用バッテリー」の行を基準として、各飛行行は以下の8列で構成される。

| 列順 | 項目名 | 記録形式・仕様 |
|---:|---|---|
| 1 | 使用バッテリー | `BAT_1` ～ `BAT_7` |
| 2 | 離陸場所 | 地名文字列、または座標付き2行形式 |
| 3 | 着陸場所 | 地名文字列、または座標付き2行形式 |
| 4 | 離陸時刻 | `HH:mm`（24時間表記、例: `09:15`） |
| 5 | 着陸時刻 | `HH:mm`（24時間表記、翌日着陸も許容） |
| 6 | 飛行時間 | `HH:mm`（実飛行分数から変換、例: 25分 → `00:25`） |
| 7 | 総飛行時間（HH:MM） | `HH:mm`（開始累計＋各飛行時間の積算、24時間超も保持） |
| 8 | 飛行の安全に影響のあった事項 | 文字列（特記事項なし時は空欄または定型） |

## 4. TEST日付シート仕様

- 飛行目的が完全一致で「`アプリテスト`」の場合に限り、通常の日付シートとは完全に分離した専用シートを使用する。
- シート命名規則: `TEST_YYYY.M.D`, `TEST_YYYY.M.D_2`, `TEST_YYYY.M.D_3` …
- 通常の日常点検シートとはブロック探索・使用判定も完全に分離する。
- 内容が空欄化されて構造が利用できない古いTESTシートは再利用せず、次の連番へ進む。
- 保存完了後にTESTシートを手動削除しても、新しいUUIDによる次回テスト時には必要な連番TESTシートを再生成する。
- 同じcomplete済みUUIDの再送時は、削除されたシートを再生成・復元することはせず、complete証明から正常応答のみを返す。

### 4.1 日付ブロックの固定予約

- 日付シートのownershipは、Script Properties上のfixed commit planに`sheetName`と`blockNo`を固定して記録する。
- 未完了planの割当てはactive reservationとして扱い、別draftの新規割当てから除外する。
- 同じdraftIdの再送では同じ固定セルをbefore/intendedで照合し、別ブロックを再選択しない。
- pending中の対象セルがbefore/intended以外なら競合停止する。complete後の手動修正・空欄整理は正常運用であり、次回保存を妨げない。
- 既存のDeveloper Metadataは削除しないが、新しい保存処理では読み書きせず、ownership判定にも使用しない。

## 5. バッテリー個別シート（BAT_1 ～ BAT_7）仕様

各バッテリーシートは、13行目から212行目までの計200行をデータ履歴領域として使用する。

### 5.1 列構成

| 列 | 項目名 | 内容・形式 |
|---:|---|---|
| A | 日付 | 運航日（`YYYY/MM/DD` 形式） |
| B | 機体 | 使用機体名（`EVO Lite` または `EVO Lite+`） |
| C | 飛行目的 | 業務目的（「アプリテスト」の場合もそのまま記録） |
| D | 飛行時間（分） | 当該飛行の実飛行時間（整数、分単位） |
| E | サイクル数 | Autel Sky等で確認できた場合の充電サイクル数（任意、数値） |
| F | BAT異常・所感 | バッテリーの異常・発熱・劣化等の所感テキスト |
| G | 飛行経路・場所 | 離陸場所・飛行場所 |
| H | 予約 | 将来拡張用・予約領域 |

### 5.2 行の決定と固定予約

- 新規保存計画の作成時に、第1列（A列）が空欄である最初の行を走査して予約する。
- 予約した`sheetName`、`row`、`flightIndex`をfixed commit planへ保存し、active pendingの同じ行は別draftの候補から除外する。
- 保存再試行時は行を再選択せず、固定したA:Hの各セルをbefore/intendedで照合して二重追記を防止する。
- 表示セルの内容が保存完了後に利用者によって手動で空欄化された場合、新しいUUIDの運航はその空き行を再利用できる。
- 保存処理中（pending状態）の手動セル変更は競合検知により安全に停止する。
- 既存のDeveloper Metadataは保持するが、保存・診断・復旧・行選択の判断材料にはしない。

## 6. 機体原本と機体累計時間仕様

### 6.1 原本シート構成

- EVO Lite用: `点検整備記録_EVO Lite_原本`
- EVO Lite+用: `点検整備記録_EVO Lite+_原本`

### 6.2 累計セルの検出規則

- シート内の固定セル座標（番地）に依存せず、ラベル文字列「`点検時の総飛行時間`」をシート内から一意に検索する。
- そのラベルに隣接する右側のセルを機体累計時間セルとして動的に特定する。

### 6.3 累計計算と更新ルール

- 管理開始初期値は `00:00`（BATも `00:00`）。毎運航のリセットではなく、不明な過去時間を推測加算しない。新品Liteと中古Lite+の起算根拠は[設計第7章の起算根拠](../01_ドローン運航記録_設計書/07_点検整備・管理開始.md#機体別の累計起算根拠)で個別管理する。Lite+の初期確認記録に管理開始の説明があることは確認済みであり、両機体を一括して「起算未解決」としない。個別の法的適用範囲は同節で区別する。
- 通常運航時:
  1. 保存計画作成時に原本の累計セルから開始累計時間を読み取る。
  2. 日付シート内の各飛行行に、各飛行時間を加算した途中累計（`HH:mm`）を書き込む。
  3. 計画された全飛行の合計時間を加算した最終累計値を、機体原本シートの累計セルへ反映する。
  4. 同一運航内で2機種を使用した場合は、機種ごとに独立して計算・更新する。
- アプリテスト時:
  - 正式な機体累計を開始値として読み取り、TEST日付シート内では飛行ごとの積算累計を表示するが、**機体原本シートの正式累計セルは絶対に更新しない**。
- 点検整備記録原本の手動運用:
  - 点検整備記録そのものは毎回の飛行ごとの記録ではなく、定期点検、修理、部品交換等のタイミングで利用者が原本を複製して手動で記入・保管する運用とする。
  - 予定と実績を区別し、実際に行った作業の日時・場所・実施者・内容・理由・その時点の累計・確認事項を残す。未実施の交換予定を実施済みにしない。複製済みの履歴を現在累計のマスターとして使わない。
  - 条件発生時の手動補記、連続飛行・日跨ぎ、日付帳票の記事欄の自動日付との境界は[設計第2章](../01_ドローン運航記録_設計書/02_法令・運用.md)・[第5章](../01_ドローン運航記録_設計書/05_記録・手動補記.md)による。新規入力欄や帳票変更を意味しない。

## 7. セル内の場所表示と書式ルール

運航開始画面・離陸画面・着陸画面で入力された「飛行経路・場所」「離陸場所」「着陸場所」は、すべて同一の表示整形ルールを適用してセルへ書き込む。

| 入力パターン | セル表示形式 | 適用書式 |
|---|---|---|
| **名称のみ** | 入力された地名・施設名を1行表示 | 通常文字サイズ、横中央、縦中央 |
| **GPS座標のみ** | 座標文字列（`(緯度, 経度)`）を1行表示 | 通常文字サイズ、横中央、縦中央 |
| **名称 ＋ GPS座標** | 1行目に名称、2行目に改行して `(緯度, 経度)` | **文字サイズ1pt縮小**、**折り返して全体を表示**、横中央、縦中央 |

- 座標判定には、前後空白を除去（trim）した値を使用する。
- 座標形式ではない文字列入力については、入力者が意図して入力した先頭空白やタブを保持して安全に保存する。
- 表示整形の適用時も、シートの既存列幅・行高は変更しない。

## 8. 手修正後の計算継続（導入型）

保存完了後、利用者が集計値を訂正した場合は、その値を基準に以後の計算を続ける。過去の日付・整備記録を遡及修正して辻褄を合わせない。実行には [導入手順](rebuild-guide.md#計算継続の導入と確認) が必要で、コードが存在するだけで本番稼働済みとは扱わない。

| 対象 | 役割 | 導入後の扱い |
|---|---|---|
| 機体別原本の正式累計 | GASが現在値を読み、当該機体の分だけ加算。値の修正で関数は消えない | 既存処理を維持。過去飛行行への逆反映なし |
| 日常点検原本・日付/TESTシート | GASが値を記録 | 記録の手修正は保持。過去行を新しい計算元へ自動転用しない |
| 複製した点検整備記録 | 手動で記入・保管する実施記録 | 書換え・再計算なし |
| BAT_1～7 B7 | 時間累計、7式。導入前の式・表示値を基準として保持 | 現在の表示値を維持し、D13:D212の以後の差分を加算する補正方式 |
| BAT_1～7 B8 | 使用回数、7式 | 修正回数＋以後の件数差分 |
| BAT_1～7 B9・E3 | 最新サイクル・最終使用日、14式 | 手修正値を保持し、参照する最新履歴が変わったらその値へ更新 |
| バッテリー台帳 F5:J11 | BAT個別シートへの参照、35式 | 台帳で値を修正した場合も対応するBAT側へ補正を適用し、参照式を戻す。J列はBAT側の膨らみ欄E4へ転記 |
| バッテリー台帳 P2:P6 | 登録本数・サイクル確認数等、5式 | 現在の修正値＋以後の集計差分。修正で分類間の数値が一致しなくなることはあり得る |

`src/26_sheet_calculation_continuity.gs` が計算定義と編集ハンドラーを持つ。保存engine、fixed plan、planHash、Properties、pendingの形式は変更しない。計算定義は `scripts/source-order.json` を通して `dist/Code.gs` に結合する。

- 非表示シート `_計算継続管理` に計算元・補正値・修正時の計算元の値・更新時刻・導入前の式と表示を保存する。利用者は通常このシートを操作しない。
- 累計・回数は「手修正値＋現在の集計－修正時の集計」。表示欄を数字で上書きしても、編集トリガーが値を補正として保持して計算式を戻す。
- 例：現在の累計70分を25分に手修正し、その後10分が追加されれば35分となる。70分を再現するために過去履歴を修正しない。
- 初回導入も現在値を補正基準にする。BAT_1/6/7の既存除外分や既存TEST分を遡及加算・減算しない。
- 以後のBAT実績集計では、目的が「アプリテスト」または既定の気象付記付きアプリテストである履歴を除外する。疑似履歴の行は既存保存仕様どおり残す。
- 利用者が独自の数式を入力した場合は上書きしない。数式自体の変更を検討した結果も尊重する。
- 日付はDateのまま保持し、UTCからの単純なシリアル換算による日付ずれを起こさない。
- 不正な入力や参照先のエラーは入力値を保持して停止する。参照エラーを0に見せかけない。
- 導入はPREPARING/PREPARED/READYを記録する。途中失敗時に導入関数を再実行しても、基準値の再初期化やトリガーの重複作成をしない。導入後に変わったセルは勝手に戻さない。

### 適用限界

1. この方式は「差分が加わる計算の継続」であり、シートや行列の任意の構造変更を自動復元する機能ではない。BAT・原本そのものの削除、見出し削除、行列移動は参照・保存先を失わせる。意図した削除を勝手に復元しない。
2. 履歴値の修正・空欄化で現在の集計が変われば、その差分も現在値へ反映される。履歴を削除しても累計を維持したい場合は、削除後の累計を利用者が修正して新しい基準にする。過去の削除を実飛行の取消か整理かと自動推定しない。
3. 最新値の切替は履歴の行・日付・時間・サイクルの組合せで識別する。同じ行を完全に同じ内容で再利用した場合は新しい実績と識別できない。履歴削除によって以前の組合せへ戻る場合も、利用者の意図を推測しない。
4. 登録本数等を手修正すると「登録7本なのに表示8本」等の不整合は許容される。修正値を尊重するため、自動で過去や他分類を合わせ直さない。
5. Googleの編集トリガーはAPI/GASの書込みでは発火しない。GASによる履歴追加は残っている数式が再計算するが、APIで集計式自体を数値へ上書きする操作は対象外。トリガー障害・権限失効時は自動復元を保証できない。
6. 同時編集や編集直後の障害で、トリガー処理時点までに追加された履歴をどの修正基準へ含めるかは一意に決まらない。通常の保存完了後に修正する運用を維持する。
7. 本番シートの編集権限・実トリガー・Googleによる数式再計算はローカルmockでは証明できない。導入前後の実確認が必要。

## 9. 新規保存時の必須帳票検査

| 条件 | 新規保存時の扱い |
|---|---|
| 常時（TEST／通常、0飛行を含む） | 選択機体、実施日、目的、経路・場所、カテゴリー／方法、操縦者、前11・後4点検、点検実施場所、後点検結果の両見出しを必須とする |
| 1飛行以上 | 使用BAT、離着陸場所・時刻、飛行時間、総飛行時間、安全事項の8欄。使用BATシートの8見出しも必須 |
| 技能証明番号あり | 技能証明番号の出力先を必須とする |
| 後点検異常／対応する内容入力あり | 不具合箇所・事象内容の出力先を確認する。異常または処置入力時は43行目の記事見出しを確認する |
| 日付側BAT所感 | 実原本に独立欄がないため必須にしない。BAT履歴の所感欄へ保存する既存仕様を維持 |
| 0飛行 | BAT行は作らず、BATヘッダーも検査しない。既存のブロック割当が利用する「使用バッテリー」目印は引き続き必要 |
| 既存pending | 新しいwriterを呼ばず元のfixed planを復旧する。欠けたoperationを追加・再生成しない |
| complete再送 | 帳票構造を再検査して書き直す経路へ入れない。手動訂正・日付シート削除を維持 |

検出時はMETA/DATA・BAT行・公式累計を作らない。計画前の既存処理により、原本コピーだけが残る場合はある。前段で別の安全なpendingが自動復旧される既存契約も変更していない。「全Spreadsheetが無変更になる」という保証ではない。

**未保証**：全結合範囲、保護設定、罫線、枠移動、見出しの重複、固定記事欄の結合形状、過去シート全体。見出し検査だけであらゆる構造破損を検出したとはしない。正常時の記事欄欠損は必須条件外。異常時の記事出力先は現原本の固定位置を前提とする。異なる帳票変種は新規保存が停止する可能性がある。

旧pendingは元planを再生成しない。出力不足が実際に存在する場合の確認手順は [再構築ガイド](rebuild-guide.md#保存証明と旧pendingの移行条件) を参照する。
