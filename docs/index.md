# ドキュメント体系・目的別インデックス

本書は全文書の役割と文書管理規則の正本。設計・仕様変更は [01設計書の00_目次.md](../01_ドローン運航記録_設計書/00_目次.md) から担当章を選び、必要な専門docsの該当節、対象コードへ進む。章一覧は00目次だけで管理し、通常作業で全章・全docsを読まない。コード所在の調査はcode-mapから、文書整理は本書から始める。

## 現在の正式仕様

| 知りたい内容 | 正本・入口 | この文書が管理する内容 |
|---|---|---|
| 設計理由・運用・仕様間の関係 | [01設計書](../01_ドローン運航記録_設計書/00_目次.md) | 目次＋8章で1冊。法令・運用、画面、保存、記録、機体/BAT、点検整備、品質の判断 |
| AIの作業規約・読書ルート | [AGENTS.md](../AGENTS.md) | 毎回守る短い規約。詳細仕様は置かない |
| 技術構造・データ契約 | [architecture](architecture.md) | 依存方向、公開API、session・plan、永続化、入力境界・検出限界 |
| 対象コード・関連試験 | [code-map](code-map.md) | 変更目的から最初に読むファイルと関数を選ぶ索引 |

設計章は独立した8冊ではなく同じ1冊の本文であり、専門docsは責務別の独立文書として維持する。コードの実装事実はsrc、意図する仕様・採用判断は担当正本で確認する。食い違う場合は、履歴・関連仕様・試験から実装不具合か文書の古さかを判断し、コードまたは文書を機械的に優先して書き換えない。

## 文書更新の恒久ルール

1. 設計・仕様変更は「00目次で担当章を選ぶ → 必要な設計判断を担当章へ反映 → 必要な専門docsを更新」の順に行う。変わらない文書へ同じ説明を追記しない。仕様の詳細は担当正本に置き、他文書は短い要約と該当節へのリンクにする。
2. 通常は新章・新docs・報告書を作らない。新設は、既存の章・正式文書に自然に収まらない独立した恒久的責務が生まれた場合のみ。その責務と既存文書で不足する理由を示し、索引とcheckerの許可一覧を同時更新する。章追加は00目次と `designChapters` を更新し、本書の1冊としての位置づけも確認する。作業日や修正案件を章にしない。
3. Markdownの配置はルートのAGENTS・README、01設計書の目次＋許可章、docs直下の許可された正式文書、`docs/reports/` に限る。別のdocs下位フォルダを作って増殖制限を回避しない。既存の画像・PDF等の配置にはこのMarkdown規則を適用しない。
4. reportsは大規模監査、重要障害、法令調査、リリース判断等の独立した証拠・経緯が必要な場合だけ作成する。作成理由・確認日・対象版・確認範囲を残し、現在の仕様・制約・導入条件は同じ変更で担当正本にも反映する。通常保守でreportsを必読にしない。
5. reports先頭12行以内に次の注意書きと担当正式文書へのリンクを置く。過去の未実装・未commit・未deployは記録当時の状態であり、現在の課題・本番状態を示す証拠として使わない。既存reportsの日時付き証拠と採用判断の訂正経緯は保持する。

```markdown
<!-- document-kind: historical-report -->
> この文書は作成・追記日時点の作業・監査記録であり、現在仕様の正本ではありません。
> `未実装`、`未commit`、`未deploy` 等は記録当時の状態です。現在仕様は [docs/index.md](../index.md) から正式文書を参照してください。
> この報告に関係する現在の正式仕様：[担当正式文書](../spreadsheet-spec.md)。
```

6. 文書追加・移動・見出し変更では索引と全参照元を更新し、[文書checkerと自己試験](test-spec.md#文書構造の検証) を実行する。checkerは配置・参照を検査し、仕様の転記漏れ・意味の整合性は差分レビューで確認する。正式文書に時点不明の作業結果を残さず、必要な状態は確認日・対象版とともに記す。
