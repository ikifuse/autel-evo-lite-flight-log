## ドキュメントの役割分担

無駄なコンテキスト消費と記述の重複を防ぐため、各文書は明確に役割を分担している。

```text
AGENTS.md → docs/index.md（目的別の入口）
  A. 01_ドローン運航記録_設計書.md（親：全体設計・共通原則・案内）
  B. docs/直下の正式仕様（責務単位の詳細）
     architecture / code-map / invariants / feature-guide
     spreadsheet-spec / test-spec / rebuild-guide
  C. docs/reports/（過去経緯を調べる場合のみ。正本ではない）
```

01設計書は親文書として要約と参照を持ち、詳細を無制限に増やさない。詳細仕様の追加先は責務単位で選ぶ。既存文書に自然に収まらない新しい独立領域だけ新規正式文書を検討する。その場合、恒久的な責務・既存文書で不足する理由を明記し、本索引の位置付けと配置チェックの許可一覧を同時更新する。「作業結果を説明したい」「調査したから」だけでは新規正式文書を作らない。

## 開発・保守時の参照ルール

1. **必要な文書だけを読む**:
   一度にすべてのドキュメントを読み込まず、上記「目的別の最短ナビゲーション」に従って該当文書のみを参照すること。
2. **正本を遵守する**:
   コードの正本は `src/` 配下であり、ドキュメントの記述と実コードに差異がある場合は、不変条件に抵触しない限り実コードおよび正本仕様書の記述を優先すること。

## 文書更新の恒久ルール

1. 仕様が変わるかを判断し、上の役割表から担当する既存正式文書を更新する。通常の機能追加・修正はこれで完了し、新しい報告書は作らない。
2. 大規模監査、重要障害の検証経緯、法令調査、リリース判定、将来の原因分析に必要な検証など、独立した履歴を残す明確な理由がある場合だけ `docs/reports/` に作る。作成理由・確認日・対象版・確認範囲を本文に残す。
3. 報告で確定した仕様・制約・運用・不変条件・導入条件は、同じ変更で担当正式文書にも反映する。報告書は経緯と証拠を持ち、現在仕様はリンク先の正式文書を参照する。過去本文の未実装・未commit・未deployを現在状態と混同しない。
4. reports冒頭は以下を共通書式とし、関連する正式文書へのリンクも追加する。

```markdown
<!-- document-kind: historical-report -->
> この文書は作成・追記日時点の作業・監査記録であり、現在仕様の正本ではありません。
> `未実装`、`未commit`、`未deploy` 等は記録当時の状態です。現在仕様は [docs/index.md](../index.md) から正式文書を参照してください。
> この報告に関係する現在の正式仕様：[担当正式文書](../spreadsheet-spec.md)。
```

5. 追加・移動時は本索引・README・参照元リンクを更新し、文書構造チェックを通す。正式文書を増やすのは既存の役割で扱えない理由がある場合のみ。意図した体系変更では本索引と `scripts/check-docs.mjs` の正式文書一覧を同時更新し、レビューする。
6. 通常の保守は正式文書だけを読む。履歴との矛盾は現行コード・正式仕様で確認し、過去の検証結果や保留判定だけで現在の仕様を決めない。自動検査は配置・参照を検査し、仕様の転記漏れや意味の正しさはレビューで確認する。
