# 長期再送対策・実帳票照合（2026-09-10 続報）

前回の局所修正を維持して、長期再送の二重保存と帳票欠損を調査した。今回のローカル実装は、完了証明の永久保持・詳細縮小と、実原本の安全事項見出しへの対応。全般的な帳票欠損時の拒否仕様は下記の具体案として分離し、未実装。commit / push / deploy、実Spreadsheet・実Propertiesの変更は行っていない。

## 1. 30日超過再送をどう解決したか

**30日を削除期限として扱うのをやめ、同一METAキーの完了証明を無期限保持する。** 30日経過後に除くのは詳細情報だけ。新しい台帳、Spreadsheetの非表示シート、Developer Metadata、クライアントのID管理操作は追加しない。

| 候補 | 評価 |
|---|---|
| 保持期間を1年等へ延ばす | 期限後に同じ問題が再発するため不採用 |
| 詳細METAを全件永久保持 | 単純だが不要な進捗・結果hash等の容量を使い続ける |
| 同一METAキーの小さな完了証明を永久保持 | **採用**。読取経路を増やさず既存complete判定を利用できる |
| 別の永続台帳・外部DBへ移す | 容量は拡張できるが、台帳障害・移行・複数保存先の整合性を追加する。現在の一人運用には過剰 |
| Spreadsheet実値から同一保存を推定 | 手動編集・空欄整理・TESTシート削除が正常運用なので証明にならない |
| 古い運航日なら一律拒否 | 未送信の長期下書きと完了再送を区別できず、長期未使用運用を制限する |

`src/19_commit_retention.gs`は30日後、`version / draftId / signature / state / stage / chunkCount / completedAt`だけを同じキーへ残す。一度削除して別キーへ移す方式ではなく、単一キーの置換。書込み前例外なら旧META、書込み後の応答消失なら新証明が残る。どちらでもcompleteとして再送を扱う。繰返しcleanupで同じ証明を書き直さない。

新規保存～VERIFIED～complete確定～DATA削除の順序は変更していない。期限経過だけで証明を削除する経路を取り除いた。再送は既存の署名照合とcomplete分岐で終わり、過去の計画を再適用しない。新しい運航日・draftIdの利用期限は設けない。

### 移行前に消失した証明の限界

保証対象は、**新コードへ切替時に残っているcomplete、および新コードで今後completeするdraft**。新コードで証明を期限削除することはない。旧コードですでに削除した証明、Propertiesの手動削除・消去までは復元できない。

これは重要な移行条件である。UUID v4には発行日時や完了状態がなく、証明のない同じ入力は「初めて送る長期下書き」と「過去に保存済みだが証明を消した再送」のどちらにもなり得る。手動編集可能な帳票の内容だけで安全に区別できない。**消失済み証明まで救済した、という意味で全過去draftの保証を達成したとはしない。** 今回、実GASのPropertiesを読む手段は使っておらず、既に削除済みの証明があるかは未確認。

デプロイ前に実Propertiesの保持状況と旧コードのcleanup実行履歴を確認する。消失が判明した場合、証拠のある完了履歴からの復元、または「証明のない旧入力は自動保存しない」移行方針と新規入力識別方式が必要。推定でcomplete証明を作ったり、未知入力を勝手に新しいdraftへ置き換えたりしない。旧TTL削除コードへ戻すと新証明も削除されるため、ロールバック版にもこの削除禁止を含める必要がある。

## 2. Properties容量

ローカル例では証明のキー＋値が**280byte/運航**。GASのbase64表現等により数byteの差があり得るので実測が必要。30日以内の詳細META・pending DATA・その他Propertiesは別途必要。1000件なら証明だけで約280KBとなる。

400KiBのアプリ側保護上限は維持。新規planの見積りと実容量確認も維持し、超える場合は新規保存を停止する。証明の自動追出しはしない。約399KiB（408,800byte）まで完了証明で埋めたローカル試験で、既存complete再送は成功、新規保存は業務セル・証明を変えず拒否した。

公式上限は単一値9KB、Properties全体500KB。アプリの保護上限と実Google割当は別である。[Google公式割当](https://developers.google.com/apps-script/guides/services/quotas)

容量不足時の案内から「古い保存計画を整理」を外し、保守を依頼する文面に変更した。利用者にdraftIdの選別・証明削除を要求しない。有限のPropertiesだけで無限件の厳密な履歴を保持し続けることはできないため、保存件数が増えた際には保守側の容量移行が必要。**安全性を優先した停止であり、永久に容量不足にならないという保証ではない。** 飛ばない期間が長いだけでは容量は増えない。

## 3. 既存complete / pending互換性

- 同じMETAキー・version 2・draftId・signatureを維持。既存completeはそのまま受理し、30日超なら同じキー内で縮小する。
- 縮小後も`state=complete / stage=COMPLETE / chunkCount=0`なので、既存の完了判定・復旧APIの完了応答・TEST破棄拒否と互換。
- 30日後の**complete詳細**からplanHash/resultHash等は省略する。pendingのplan JSON/hash/operation/順序/before/intendedには変更なし。
- 旧Git基準でcomplete / pendingを作り現コードへ移す追加試験と、従来の分割互換試験を実行する。長期証明削除だけは意図した仕様変更であり、旧挙動との同値を要求しない。
- cleanupのMETA破損時DATA保護、UUID/version検証、診断注入対策、戻る履歴の通信除外は維持。

## 4. 手動Spreadsheet修正

完了証明は業務帳票の正しさを検査する台帳ではなく、「同じ保存要求を実行済み」という証明。再送時に過去の値を復元しない。場所/書式/BAT備考/正式累計の手動訂正、日付シート削除後の再送を31/366/3660日相当で試験し、追加書込みがないことを確認する。同一IDの入力内容変更は従来どおり拒否する。

## 5. 実帳票と欠損時の扱い

Google Drive / Google Sheets connectorを読み取り専用で使用。対象はsrcのSPREADSHEET_IDと一致する[EVO Lite 運航記録](https://docs.google.com/spreadsheets/d/10PMEteELQRRWnqc5mVmF6tQCfxFEJEGe2LitpDhYqk8/edit)。確認範囲は`日常点検!C1:AD45`、`BAT_1～7!A12:H12`、両機体原本`E5:H7`等。実GASでコードを実行した確認ではない。

実原本の重要な対応：

| 項目 | 実原本の位置・内容 |
|---|---|
| 日付 | J8 / Y8 |
| 目的・場所・飛行方法 | C11:C13 / R11:R13 |
| 操縦者・技能証明 | K11:K12 / Z11:Z12 |
| 前点検11項目 | C19:C29 / R19:R29、確認はI列/X列 |
| 後点検4項目 | J19:J22 / Y19:Y22、確認はO列/AD列 |
| 点検場所、異常、詳細 | J24、L25:L26、J27:J28等、右ブロックにも対応欄 |
| 飛行見出し | 33行目、No.1はC/E/G/I/J/K/L/N、No.2はR/T/V/X/Y/Z/AA/AC |
| 安全事項 | **飛行の安全に影響のあった事項** |
| BAT異常・所感 | 日付側の独立欄は確認範囲にない。BAT各シートF12は「異常・所感」 |
| 正式累計 | 両機体原本E6が見出し、G6が値 |

現コードは実安全事項見出しを別名一覧に持たず、指定された安全事項を日付側へ出力しない経路があった。**これは現仕様の出力漏れとして、`21_sheet_records.gs`の別名追加だけを実装**。実見出し名で文字列が保存される回帰テストを追加した。保存済みpendingには新しいoperationを追加しないので、過去planの出力漏れを自動修復する変更ではない。

### 欠損の再現と結論

ローカルfixtureで場所見出し、操縦者見出し、離陸場所見出し、後点検「発熱」をそれぞれ消すと、いずれもcompleteに到達する例を確認。必須項目を欠いたままcompleteするより、**新規planの作成段階で安全停止する方針を推奨**する。

ただし一律の「見出しが1個なければ停止」は不適切。実原本は飛行8項目、既存モックはBAT所感を含む9項目。技能証明・異常詳細等の入力/出力条件も異なる。後点検の同名項目は前点検にもあるため、ブロック全体の単純検索では欠損を見逃す。

### 要判断：具体的な拒否仕様（未実装）

1. **常時必須**：対象ブロックの機体・日付・目的・場所・操縦者・飛行方法、前後点検の見出し/確認欄、後点検場所。前後点検は別々の列区画で識別し、欠損・重複・書込先がラベル内になる結合異常を拒否する。
2. **1飛行以上で必須**：実原本の8飛行項目、7行の記録領域、使用BATシートのA:Hの対応。0-flightでBAT出力欄を要求しない。
3. **入力時必須**：技能証明が入力されていればその出力欄、異常時は不具合/内容/記事・確認欄、処置入力時は処置欄。空欄正常運航で異常記事欄まで必須にするかは別判断。
4. **日付側の必須対象外**：BAT異常・所感の独立欄。現原本にはないためBAT側へ保存する現在仕様を維持する。第9列を勝手に作らない。
5. **既存pending**：新しい必須判定からplanを再生成しない。既存plan自体が必須operationを欠く場合、そのまま復旧を許すか、安全停止して手動確認へ回すかを決める必要がある。新しいカタログで古いplanを書き換えない。
6. **complete再送**：帳票の構造検査に入れない。完了後の手動編集/シート削除を理由に書き戻さない。

この拒否仕様は、これまで許容していた帳票変種・既存pendingの復旧可否を変えるため、今回勝手には実装していない。**帳票欠損時の黙った省略は、別名修正だけでは解消していない。** デプロイ前に上記の適用範囲を決める必要がある。全結合範囲・保護設定・実データ全体の照合は未実施。
