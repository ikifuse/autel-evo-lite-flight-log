# テスト・品質検証仕様書

## 1. 文書の位置づけ

本書は、Autel EVO Lite / Lite+ ドローン運航記録システムにおける回帰テスト、障害注入テスト、セキュリティ試験、およびアプリテストの動作検証仕様を定めたドキュメントである。

- 関連正本仕様書: [01_ドローン運航記録_設計書.md](../01_ドローン運航記録_設計書.md)
- スプレッドシート帳票仕様: [docs/spreadsheet-spec.md](spreadsheet-spec.md)
- コード対応索引: [docs/code-map.md](code-map.md)
- テスト実装ファイル: `tests/regression.test.js`
- テスト実行対象: 自動生成された `dist/Code.gs`

---

## 2. テスト方針と実行環境

本システムのテストスイート `tests/regression.test.js` は、Google Apps Script（GAS）の各ランタイムAPI（`SpreadsheetApp`, `PropertiesService`, `CacheService`, `LockService`, `HtmlService` 等）を忠実に模擬したNode.js環境で動作する。

- **対象コード**: `scripts/build.mjs` によって生成された `dist/Code.gs` を直接ロードして検証する。
- **GAS固有API境界**: Developer Metadataのモックは、実GASが対応するSheet全体・行全体を許可し、任意セル・部分Rangeへの追加を例外にする。NodeモックのPASSだけを実GAS実行済みとは扱わない。
- **検証の基本原理**:
  1. 「障害なしで1回保存した結果」と、
  2. 「処理途中で意図的に障害・例外を注入し、その後同一UUID（draftId）で再送・再試行した結果」
  が、日付シート、BAT個別履歴、機体原本累計、complete証明のすべてにおいて**完全一致すること**を自動照合する。

## 3. 基本回帰テスト（TEST 1 ～ 15）

通常の運航フロー、シート切り替え境界、データ整合性を網羅するテスト項目群。

| テストID | 検証内容・対象 | 期待される振る舞い・合否基準 |
|---|---|---|
| **TEST 1** | 単一機体・3飛行 | No.1ブロック内に3行正しく記録され、BAT履歴、機体累計が整合すること |
| **TEST 2** | 単一機体・7飛行（ブロック上限） | No.1ブロックの最大上限（7行）まで漏れなく記録されること |
| **TEST 3** | 単一機体・8飛行（ブロック溢れ） | 7飛行目がNo.1、8飛行目がNo.2ブロックへ跨いで正しく記録されること |
| **TEST 4** | 単一機体・14飛行（シート上限） | No.1に7行、No.2に7行記録され、1シートの上限14飛行を収容できること |
| **TEST 5** | 単一機体・15飛行（シート溢れ・連番） | 14飛行が初日シート、15飛行目が連番シート（`_2`）のNo.1へ記録されること |
| **TEST 6** | 同一運航内での機体交代 | 交代前機体がNo.1、交代後機体がNo.2ブロックへ割り振られ、各機体累計が独立更新されること |
| **TEST 7** | BAT重複防止 | 同一運航または複数運航でBAT行が二重書き込み・上書きされないこと |
| **TEST 8** | 天気・風向・風速の任意入力 | 未入力時は空欄のまま保存され、エラーにならないこと |
| **TEST 9** | 日付またぎ飛行 | 23:55離陸〜翌日00:10着陸等の実時間計算が正しく `HH:mm` で集計されること |
| **TEST 10** | 24時間を超える総飛行時間 | 機体累計・行累計が24時間を超えても正しく加算・表示されること |
| **TEST 11** | 補助者履歴の管理 | 氏名のtrim、重複除去、履歴選択肢の整合性、未選択時は空欄保存 |
| **TEST 12** | 画面遷移と保存後状態 | 保存成功後に `STATE.active=false`, `STATE.session=null` のトップ状態へ復帰すること |
| **TEST 13** | 場所入力の3形式表示 | 名称のみ／GPSのみ／名称＋GPS（2行折返し・1pt縮小）のセル書式が適用されること |
| **TEST 14** | 廃止済み機能の無効化確認 | 旧お気に入り現場機能等の残骸が混入していないこと |
| **TEST 15** | UIテンプレートハッシュ検証 | `src/web/` からアセンブルされた `APP_HTML` のSHA-256ハッシュが期待値と一致し、意図しないUI破壊がないこと |

## 4. 障害注入テスト（T16 ～ T23）

固定commit planの冪等性とロールフォワード機構を証明するため、各保存フェーズの直前・直後で強制的に例外を発生させ、再試行時の挙動を検証する。

| テストID | 障害注入ポイント | 再試行時の検証要件 |
|---|---|---|
| **T16** | 日付シート書込み直後 | 日付シートが既に書き込まれていることを検知し、二重書き込みせずBAT履歴へ進むこと |
| **T17** | BAT_1書込み直後 | BAT_1のDeveloper Metadataを照合し、BAT_1をスキップしてBAT_2以降を書き込むこと |
| **T18** | BAT_2書込み直後 | BAT_1およびBAT_2を重複追加せず、残りのBATおよび点検へ進むこと |
| **T19** | 飛行後点検書込み直後 | 点検記録の完了を検証し、機体累計更新フェーズへ正しく進むこと |
| **T20** | EVO Lite累計更新後、EVO Lite+更新前 | EVO Liteの累計を二重加算せず、EVO Lite+のみを加算して整合させること |
| **T21** | 最終flush直前 | 全セル・行の計画値読み戻し検証を行い、欠落なくcompleteへ移行すること |
| **T22** | complete保存直前 | 計画の全ステップが完了していることを確認して安全にcomplete証明を発行すること |
| **T23** | complete後・クライアント応答前 | サーバー側は保存完了済み。再送時にスプレッドシートや累計を一切増やさず、complete証明から即座に成功応答を返すこと |

### 4.1 追加障害耐性試験

スイート内では上記T16〜T23に加え、以下の異常系シナリオも検証する。

- **シートコピー競合**: 日付シート作成時の衝突防止。
- **ロック競合**: `ScriptLock` 取得失敗時に安全に再試行エラーを返すこと。
- **入力改変の拒否**: complete済みUUIDに対して改ざんされた入力で再送された場合、400/エラーとして拒否すること。
- **セル手動変更検知**: pending計画が存在する状態で対象セルが第三者に書き換えられた場合、上書きを停止して競合エラーとすること。
- **チャンク欠落検知**: PropertiesService内の分割DATAチャンクが一部欠落・破損している場合、復旧処理を停止すること。

## 5. アプリテストの検証仕様

飛行目的「`アプリテスト`」が指定された場合の特殊挙動に関する検証仕様。

1. **TEST日付シートの分離検証**:
   - `TEST_YYYY.M.D` シートが生成され、通常の日付シートと混ざらないこと。
2. **途中累計と原本累計の分離検証**:
   - TESTシート内の飛行行には、正式累計を開始値とした途中加算累計が表示されること。
   - **`点検整備記録_*_原本` の正式機体累計セルは一切更新されず、値が変わらないこと**。
3. **BAT履歴の連携検証**:
   - 通常運航と同様にBAT個別シートへ1行保存され、飛行目的に「アプリテスト」と記録されること。
4. **手動削除と再生成の検証**:
   - 保存完了後にTESTシートを手動で削除した場合、次回アプリテスト（新規UUID）で新たな連番TESTシートが正常に生成されること。
5. **同一UUID再送の検証**:
   - TESTモードにおいてもT23等の同一UUID再送が正常に機能し、二重記録されないこと。

## 6. セキュリティーと入力検証仕様

### 6.1 数式インジェクション（Formula Injection）対策の検証
- 自由入力欄（飛行目的、場所、特記事項、所感等）に `=`, `+`, `-`, `@` で始まる文字列が入力された場合、セルへ `RichTextValue` として保存されること。
- シート側で `getFormula()` を呼んだ結果が必ず空文字（`""`）となり、数式として評価・実行されないことを検証する。

### 6.2 不正入力・境界値の事前拒否
以下の異常入力に対し、スプレッドシートやPropertiesServiceを1行も変更することなく、保存入口で事前拒否されることを検証する。
- 不正な機体モデル名、1〜7以外のBAT番号、`op_` プレフィックスのないUUID。
- 1900年や2200年などの範囲外日付、0分や241分以上の異常飛行時間、1440分超の1運航合計。
- 30飛行を超える過剰配列、512KiBを超える巨大ペイロード、プロトタイプ汚染キー（`__proto__` 等）。

## 7. テスト実行コマンドと合否判定

開発時・変更時は、以下の手順でビルドとテストを全件実行する。

```bash
# 1. ソースコードの結合と構文チェック
node scripts/build.mjs

# 2. 生成された dist/Code.gs とソースの完全整合性チェック
node scripts/build.mjs --check

# 3. 回帰テスト・障害注入テストスイートの全件実行
node tests/regression.test.js

# 4. Git差分・空白不整合のチェック
git diff --check
```

**合否判定基準**:
- すべてのテストケース（TEST 1〜15、T16〜T23、追加障害試験、セキュリティー試験）が `PASS` すること。
- テスト実行結果に `FAIL` または未処理の例外が1件も存在しないこと。
- `build.mjs --check` が成功し、`dist/Code.gs` が最新の `src/` から忠実に生成されていること。
