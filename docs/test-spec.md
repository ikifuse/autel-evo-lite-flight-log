## 1. 文書の位置づけ

本書は、Autel EVO Lite / Lite+ ドローン運航記録システムにおける回帰テスト、障害注入テスト、セキュリティ試験、およびアプリテストの動作検証仕様を定めたドキュメントである。

- 関連正本仕様書: [01_ドローン運航記録_設計書.md](../01_ドローン運航記録_設計書.md)
- スプレッドシート帳票仕様: [docs/spreadsheet-spec.md](spreadsheet-spec.md)
- コード対応索引: [docs/code-map.md](code-map.md)
- テスト実装ファイル: `tests/regression.test.js`、`tests/refactor-compat.test.js`、`tests/web-compat.test.js`
- 責務境界チェック: `scripts/check-boundaries.mjs`
- テスト実行対象: 自動生成された `dist/Code.gs`

## 2. テスト方針と実行環境

`tests/regression.test.js` は、保存処理で使うGAS APIをNode.js上のモックで検証する。2026-09-10時点では95個のOKレポートを出力し、そのうち `SECURITY` の7個も全95個に含まれる。1レポートに複数の入力例・assertionを含むため、95個が個別入力の総数ではない。

- **対象コード**: `scripts/build.mjs` によって生成された `dist/Code.gs` を直接ロードして検証する。
- **GAS固有API境界**: モックにはGoogle Apps Script公式APIに存在するメソッドだけを実装し、`getEntireRow()`のような便利APIを追加しない。NodeモックのPASSだけを実GAS実行済みとは扱わない。
- **モックの限界**: 回帰モックの `flush()` とLock待機・解放はno-opであり、Cacheの実TTL、サービス容量・日次quota、実通信遅延、複数端末の同時実行は再現しない。Web試験もDOM・通信のモックを使用し、実ブラウザの描画やスマートフォン操作を確認する試験ではない。今回の責務分割後の実GAS・実機確認は未実施。
- **検証の基本原理**:
  1. 「障害なしで1回保存した結果」と、
  2. 「処理途中で意図的に障害・例外を注入し、その後同一UUID（draftId）で再送・再試行した結果」
  の日付シート、BAT個別履歴、機体原本累計の値・書式を比較し、complete証明の成立と残DATAチャンクの消去を確認する。

## 4. 障害注入テスト（T16 ～ T23）

固定commit planの冪等性とロールフォワード機構を検証するため、各保存フェーズの直前・直後で強制的に例外を発生させ、同一モック内で再試行時の挙動を比較する。

| テストID | 障害注入ポイント | 再試行時の検証要件 |
|---|---|---|
| **T16** | 日付シート書込み直後 | 日付シートが既に書き込まれていることを検知し、二重書き込みせずBAT履歴へ進むこと |
| **T17** | BAT_1書込み直後 | BAT_1の現在値がfixed planのintendedと一致することを照合し、BAT_1をスキップして残りを書き込むこと |
| **T18** | BAT_2書込み直後 | BAT_1およびBAT_2を重複追加せず、残りのBATおよび点検へ進むこと |
| **T19** | 飛行後点検書込み直後 | 点検記録の完了を検証し、機体累計更新フェーズへ正しく進むこと |
| **T20** | EVO Lite累計更新後、EVO Lite+更新前 | EVO Liteの累計を二重加算せず、EVO Lite+のみを加算して整合させること |
| **T21** | 最終flush直前 | 全セル・行の計画値読み戻し検証を行い、欠落なくcompleteへ移行すること |
| **T22** | complete保存直前 | 計画の全ステップが完了していることを確認して安全にcomplete証明を発行すること |
| **T23** | complete後・クライアント応答前 | サーバー側は保存完了済み。再送時にスプレッドシートや累計を一切増やさず、complete証明から即座に成功応答を返すこと |

### 4.1 追加障害耐性試験

スイート内では上記T16〜T23に加え、以下の異常系シナリオも検証する。

- **シートコピー後の障害**: 日付シートコピー直後に停止しても、再試行で正しい帳票へ保存すること。
- **入力改変の拒否**: pending / completeの同UUIDで入力内容が変更された場合、エラーとして拒否すること。
- **セル手動変更検知**: pending計画が存在する状態で対象セルが第三者に書き換えられた場合、上書きを停止して競合エラーとすること。
- **チャンク欠落検知**: PropertiesService内の分割DATAチャンクが一部欠落・破損している場合、復旧処理を停止すること。
- **Properties・Cache障害**: DATA途中保存、進捗保存失敗、complete META確定後の圧縮中断からの再試行、Cache利用不能を検証する。
- **先行pendingと予約**: 古い順の復旧、各draft実行直前の再診断、競合時の新規保存停止、active BAT予約を検証する。

実際のLock取得失敗・同時実行競合は、このモック試験の実証範囲に含めない。

## 5. アプリテストの検証仕様

飛行目的「`アプリテスト`」（既定の気象情報を付けた目的を含む）が指定された場合の特殊挙動に関する検証仕様。

1. **TEST日付シートの分離検証**:
   - `TEST_YYYY.M.D` シートが生成され、通常の日付シートと混ざらないこと。
2. **途中累計と原本累計の分離検証**:
   - TESTシート内の飛行行には、正式累計を開始値とした途中加算累計が表示されること。
   - **`点検整備記録_*_原本` の正式機体累計セルは一切更新されず、値が変わらないこと**。
3. **BAT履歴の連携検証**:
   - 通常運航と同様に飛行ごとにBAT個別シートへ1行保存され、飛行目的に「アプリテスト」が含まれること。
4. **手動削除と再生成の検証**:
   - 保存完了後にTESTシートを手動で削除した場合、次回アプリテスト（新規UUID）で空いている日付名のTESTシートを再作成できること。必ず新しい連番になるとは限らない。
5. **同一UUID再送の検証**:
   - TESTモードにおいてもT23等の同一UUID再送が正常に機能し、二重記録されないこと。
6. **0-flightとTEST保留の検証**:
   - 通常/TESTとも0-flightで点検を保存でき、BAT履歴・正式累計を変更しないこと。
   - TESTの実データが残るpendingは破棄せず、実データのない削除済み/空再作成シートの安全残骸だけを解除できること。

## 6. セキュリティーと入力検証仕様

### 6.1 数式インジェクション（Formula Injection）対策の検証

- 自由入力欄（飛行目的、場所、特記事項、所感等）に `=`, `+`, `-`, `@` で始まる文字列が入力された場合、セルへ `RichTextValue` として保存されること。
- シート側で `getFormula()` を呼んだ結果が必ず空文字（`""`）となり、数式として評価・実行されないことを検証する。

### 6.2 不正入力・境界値の事前拒否

以下の異常入力に対し、スプレッドシートやPropertiesServiceを1行も変更することなく、保存入口で事前拒否されることを検証する。

- 不正な機体モデル名、1〜7以外・非整数・文字列のBAT番号、不正な `op_` + UUID v4形式。
- 1900年や2200年などの範囲外日付、0分や241分以上の異常飛行時間、1440分超の1運航合計。
- 30飛行を超える過剰配列、512KiBを超える巨大ペイロード、深度・プロパティ件数の上限超過。

このほか、正常入力の上限値、Properties容量不足、plan容量見積超過、同UUID冪等性を検証する。7個の `SECURITY` レポートはこれらの回帰試験であり、全ての攻撃方法・認証設定・実GAS quotaを監査した結果ではない。

## 7. 責務分割の互換・境界試験

### 7.1 サーバーの基準コミット互換

`tests/refactor-compat.test.js` は、承認済みB案基準 `b8e1ab6723784216b119c27d6bf9c2c540e5adb5` のGit blobと現在の `dist/Code.gs` を、同一モック・固定日時・入力で比較する。基準オブジェクトを含むGit履歴が必要で、実GASや利用者のSpreadsheetへアクセスしない。

- 通常、8飛行、2機体交互運航、気象付きTEST、通常/TESTの0-flight、Formula Injection文字列について、plan JSON・operation順・UTF-8チャンク境界・planHash・入力署名・応答を比較する。
- セルsetter、Properties read/write/delete、flush、Lockの呼出順を比較する。実サービスの遅延や原子的実行を再現する試験ではない。
- adapterの8種類のkindについて、通常文字列とDate表現objectのsetter引数を基準版と比較する。値のDate復号が書式・配置・font・wrapへ広がらないことも確認する。
- 基準コードが残したpendingを現在コードへ移し、対象障害点から同じplanHashでroll-forwardできることを検証する。
- 基準コードのcomplete後にDATE/BAT/正式累計を手動修正し、同UUID再送が業務セルへ書かないこと、およびpendingの第三者変更を競合停止することを検証する。
- 公開GAS入口6関数とinternal関数名の末尾 `_` を検査する。

意図した機能変更では、B基準との完全同値を要求する範囲を先に見直す。基準SHAや期待値を機械的に更新して差異を隠さない。

### 7.2 Web互換

`tests/web-compat.test.js` は同じB基準の結合Webスクリプトと現在版を、NodeのVMと簡易DOM・localStorage・RPC・GPSモックで比較する。

- 起動、飛行各phase、BAT交換、機体交代、戻る操作、画面入力退避、旧下書き復元、storage不能、異常点検、0-flight、中止を比較する。
- offline時の下書き保持、確定保存payload、成功/失敗応答、描画→下書き削除→完了通知の順序、描画失敗時の下書き保持を比較する。
- 診断/復旧/破棄のRPCと表示、GPS成功・逆ジオコーディング失敗・位置情報取得失敗を比較する。
- 依存注入に伴う承認済みhandler名だけを正規化してHTMLを比較する。診断競合詳細のHTMLエスケープは承認された挙動差として個別検査し、危険なタグが文字列として表示される出力を確認する。

最終確認では `--allow-legacy-diagnostic-html` を付けない。実DOMでのスクリプト実行、レイアウト、ブラウザ権限、実ネットワーク通信はこの試験の範囲外。

### 7.3 責務境界とチェック自体の検証

`scripts/check-boundaries.mjs` は両source-orderのファイル一覧、global重複、公開GAS入口6関数、internal末尾 `_`、凍結Legacyへの逆参照、純粋なcodec/time/compareへのGAS API・非純粋依存、server/Webの直接global参照による循環を検査する。`--json` で参照元の行とsymbolを含む依存一覧を出力できる。

`--self-test` の10シナリオは、文字列・コメント・正規表現・template rawの誤検出防止、template式の参照、重複、複数可変宣言、関数/状態の循環、public/pure/Legacy境界、portsとbootstrapを検証する。

このチェックは字句解析であり、動的呼出し、計算したプロパティ名、alias、eval、HTMLイベント文字列、注入先portsの実行時経路は解決しない。local変数がglobalと同名の場合は余分な依存を報告し得る。bootstrapの結線とmutation経路は互換試験・レビューでも確認する。

## 8. テスト実行コマンドと合否判定

作業中は変更した責務の関連確認を先に行い、最終確認では以下を実行する。

```bash
# 1. ソースコードの結合と構文チェック

# 2. 生成された dist/Code.gs とソースの完全整合性チェック

# 4. サーバー / Webの基準互換確認

node scripts/check-boundaries.mjs
node scripts/check-boundaries.mjs --self-test

# 6. Git差分・空白不整合のチェック
git diff --check
```

**合否判定基準**:

- すべてのテストケース（TEST 1〜15、T16〜T23、追加障害試験、セキュリティー試験）が `PASS` すること。
- テスト実行結果に `FAIL` または未処理の例外が1件も存在しないこと。
- `build.mjs --check` が成功し、`dist/Code.gs` が最新の `src/` から忠実に生成されていること。
- 構造整理ではサーバー/Web互換試験と境界チェックが成功すること。実GAS・実機で実施した確認は、これらのNode試験とは分けて報告する。

既存CIの `.github/workflows/build-dist.yml` にも回帰・両互換・境界チェックと自己試験を接続している。基準Git blob参照のためcheckoutは `fetch-depth: 0` を使用する。今回の変更後の実GitHub Actions実行は未確認であり、ローカルPASSと区別する。
