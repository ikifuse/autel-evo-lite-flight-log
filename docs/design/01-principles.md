# 第1章 目的・設計思想・基本原則

[設計書目次](../../01_ドローン運航記録_設計書.md) · [文書索引](../index.md)

本章はシステムの目的、設計判断の基準、全体をつなぐ構成を扱う。具体的な不変条件は [invariants](../invariants.md)、責務と依存方向は [architecture](../architecture.md) を正本とする。

## 目的と判断基準

本システムの目的は、飛行日誌に必要な記録と機体・バッテリーの保守情報を残しながら、ワンオペ現場の操作負担を抑えることである。

設計判断には次の7条件を使う。

1. 法規・安全上、本当に必要か。
2. その時点で現物またはアプリから確認できるか。
3. 自動取得または前回値の引用にできないか。
4. 必須化が現場操作を妨げないか。
5. 初期値による虚偽記録が起きないか。
6. 戻る・中断・圏外・再試行でも正確さを保てるか。
7. 最後に正式記録として不足なく残るか。

ワンオペの連続飛行では、最初の全点検、BAT交換時の最小確認、最後の飛行後点検を組み合わせ、各飛行は1行ずつ残す。入力中は端末に下書きを持ち、全工程終了時に一括保存する。操作を減らす判断と記録を省略する判断を混同しない。

アプリは記録支援であり、許可・承認判断、飛行可否、安全確保、機体整備を代替しない。正式記録の役割分担と判断根拠は [第2章](02-legal-operation.md)、現場操作は [第3章](03-workflow-ui.md) に置く。

## 全体構成と責務の分離

Google Apps ScriptのWebアプリが単一ページのUIを提供し、固定のGoogleスプレッドシートへ記録する。タイムゾーンは `Asia/Tokyo`。端末の運航状態・下書き、サーバーの固定保存計画、保存完了後の業務帳票を分け、それぞれの役割を越えて復元・上書きしない。

- 端末は画面入力と運航の進行を保持し、最終保存まで帳票へ逐次書き込まない。
- サーバーは入力を検証して保存先・値を固定し、失敗しても同じ計画で完了へ進める（[第4章](04-save-recovery.md)）。
- Spreadsheetは人が訂正・補記できる正式帳票である。完了後の手修正とpending中の競合は別に扱う（[第5章](05-records-manual.md)）。
- 飛行明細、BAT履歴、機体正式累計、複製した整備実施記録の責務を分ける（[第6章](06-aircraft-battery-totals.md)、[第7章](07-maintenance-start.md)）。

UI、保存の統括、計画・永続化・比較・復旧、帳票操作を分離し、変更時に必要な責務だけ読める構成を保つ。Webの画面は共通portを通して状態取得・操作を要求し、bootstrapが具体的な接続を行う。共有グローバルを利用する構成であり、ファイル分割自体がアクセス制御になるわけではない。

使用サービス・API、ソース責務表、session形式、ビルド順は [architecture](../architecture.md)、担当コードは [code-map](../code-map.md) を参照する。設計書内にこれらの一覧を複製しない。品質と変更時の確認範囲は [第8章](08-security-quality.md) に従う。
